# 即梦视频快线

目标：把连接、素材上传、视频准备和积分确认接成可恢复的短流程，减少重复发现与重复操作。
复用已安装 `dreamina-canvas-cli`；首次使用时读取其 SKILL.md，协议问题按需读对应 reference，同一会话不反复加载。
本技能固定编排，不替代当前 CLI 契约、服务端批准或用户当轮要求。生图、改图仍默认内置 image_gen 并保存本地。
“优化流程”不授权试生成；实际外部操作只执行用户本次请求的项目、素材和视频。

## 0. 白模出片先过对齐门禁（2026-11-04）

- 任务书开头有「〇 核验回执」的（由仓库 `.claude/skills/whitemodel-pipeline/` 流程工具生成），上传素材前先原样运行那条命令；
  隔了会话再提交，提交前再跑一次。最后一行 `RESULT_JSON` 的 `ok` 不是 true 就停，把列出的问题原样报给用户；
  不改任务书、不换图、不自行修参数，也不改走网页绕过。
- 用了白模视频（`@视频1` 是白模运镜）却没有「〇 核验回执」的手写任务书：先停下问用户，用户当轮明确说跳过核验才继续。
- 有回执的任务，素材顺序、提示词、模型、参数、节点名、下载位置和记录键都以任务书为准；本技能其余各节只管上传、报价、提交和恢复的做法。

## 1. 一次收齐输入，复用现状

- 从当前请求、已确认方案及项目 `资产/生成记录.json` 读取目标画布、提示词、素材顺序、模型、时长、比例与数量。
  只补问会改变结果且无法从已有上下文确定的信息；不要再确认已经批准的素材、上传动作或方案。
- 先确认账号/profile/region 与目标 projectId 的组合；不要把“CLI 当前画布”或记录中最后出现的画布当目标。
  无法唯一定位时才询问；已有可靠 ID 时直接读取所需节点，不列举全部画布和全部素材。
- 按内容读取任务相关记录，不把整份历史 JSON、schema 或模型目录塞进上下文；已有不同记录结构就就地兼容。
  不为本技能迁移、重写或复制整个生成记录，不动其他任务条目。

### 审核与生成沿用同一份素材映射

- 本项目的 `资产/参考素材映射.json` 按提示词相对路径保存已审核素材编号、名称、源文件路径、SHA-256 与正文 SHA-256。新写、改写或重拍的提示词交审核前由提示词流程登记。生成时从该稿的登记生成有序引用，不另外手抄一套编号。
- 上传前运行工作区 `通用工具/核对参考素材.py`，指定 `--project` 与 `--prompt`，确认正文和源素材均与登记一致。缺少登记、编号不全、正文或素材变化时，先核实与修正，不能用同名图代替。
- 源文件到图片节点或资源的对应使用本次核实的源文件 SHA-256 和生成记录。上传完成后，逐项回读目标视频节点的实际引用，核对媒体类型、数量、顺序、节点或资源 ID 与源文件映射。批量上传完成的先后顺序不能充当编号依据。
- 提交前同时核对节点实际正文和引用列表。可将节点回读整理为核对工具支持的 `--actual` 输入，其来源哈希必须来自本轮核实的节点或资源映射。不得复制期望清单伪造回读。任何一项不一致，修正草稿并再次回读后再提交。

## 2. 每次工作只做一次有效预检

- 当前执行会话首次使用 CLI：检查 `--version`、读取 `schema`；在内存筛选本次命令的 flags 和返回字段。
  同一版本、同一会话复用已读契约；跨会话或版本变化重新读取，不凭旧示例猜参数。
- 对目标 profile 执行 `auth status`。有效则继续，不重新登录、不退出账号、不重装、不创建新浏览器配置。
  只有确实未登录/过期时才按认证协议登录；已有 challenge 就继续同一次授权，不重复发起。
  用户当轮明确要求遇到登录或授权即停、且未允许网页回退时，`auth status` 返回 `loggedIn=false` 即为停止点：不发起登录、不打开授权链接；报告尚未创建或提交的状态。
  若用户明确要求“CLI 未登录或不可用就改走已登录网页”，不登录 CLI，直接使用可用的内置浏览器连接目标画布；网页要求登录、权限或授权时按用户边界停止。
  若浏览器返回 `The browser access host is unavailable`，可尝试直接打开目标画布一次；仍失败即报告浏览器连接不可用，不把它写成网站未登录，不改系统安全设置，也不使用 Windows 文件选择框绕过用户限制。
  网络超时按认证协议退避，最多额外两次；DNS/权限错误只在条件改变后复查，不切 region 或读写凭据来试错。
- 认证后，只查本次视频模型：已知名称用 `model ls <名称> --type video`，未知才用 `model ls --type video`（CLI 1.4.2 起；1.3.0 及以前叫 `model find`、`model list`，新版不认）。
  使用返回的 canonical model 与真实 mode/限制；同一批次复用目录结果，服务端拒绝时再查对应变化。
- 版本/schema 属于独立本地检查，可与本地文件哈希核对并行；模型查询必须在认证状态确认之后。
  无依赖读取可合并；画布写入、生成记录写入和有依赖动作按顺序执行，不为提速开无界并发。
- 浏览器用于登录、展示和必要的 UI 补充。复用匹配的标签页；只打开一次 CLI 返回的目标 webUrl，并发送链接。
  不用网页截图/反复切标签来代替 CLI 已暴露的上传、节点读取、报价和运行能力。
  匹配标签已被另一任务占用时，不抢占；按用户要求新建本任务的独立标签。首次导航或绑定超时后先查看标签清单和实际状态，画布可能已打开，不据此认定未登录或反复新开标签。
  本次内置浏览器恢复时，先读所选浏览器的公开文档，再用 `browser.tabs.get(<清单中的既有ID>)` 绑定已打开的目标画布，单独调用 `tab.playwright.domSnapshot()` 成功；不要把绑定、导航和首次状态读取合在一个短超时调用里。
  Chrome 返回 `Debugger unattached` 或 `Page.navigate` 超时只说明浏览器控制未完成，截图可用也不证明 DOM 可读；任务允许内置浏览器时，可确认其目标画布已登录后完成所缺网页步骤，不改系统权限、不重复上传或提交。
  用户明确要求已登录的 CLI 直接继续、忽略网页登录时，以 CLI 的认证和操作结果为准；展示画布时看到网页登录页，不构成 CLI 停止条件。后续确需网页完成而 CLI 未覆盖的步骤，再报告该步骤的实际缺口。

## 3. 按内容去重上传，一次核对引用

- 上传前依次查生成记录、画布。
- 找到就引用，两处都没有才上传。
- 画布上的图核对名字、尺寸、画面。
- 拿不准是不是同一张，停下问用户。
- 新素材一律传成独立节点，照 AGENTS.md 起名。
- 节点编号、名字和 SHA-256 记进生成记录。
- 视频节点只引用素材节点，禁止直传。

### 本机 CLI 1.2.0 反复上传异常的处理（2026-11-07）

- 本机多次出现 `cli.upload_state_unknown`，而本次同一张完整、合规尺寸的 PNG 通过已登录网页数秒内成功；CLI 保存草稿、报价和提交仍正常。当前不能证明具体是网络传输还是服务端登记故障，不把这个通用错误说成图片损坏、内容被拒或确定的超时。
- 在此机器、此版本且尚无修复证据时，任务没有明确强制 CLI 上传的新图片，优先从已登录网页左栏“上传”传成独立图片节点；已有素材仍按哈希复用。CLI 继续保存完整提示词、回读校验、报价和提交，避免每批新图重新碰同一上传故障。版本或环境变化后重新评估，不扩大成所有机器或所有媒体的永久规则。
- 已经返回未知状态的那一次上传仍按下文原 ID 核查及用户授权规则处理；上述预防性选路不授权自动重传未知请求。网页成功后保留旧请求未知事实，不能写成旧资源已恢复。调查只使用可证实的错误、文件验证与日志，系统代理和 CLI 代理差异仅是线索，没有对照证据就不归因为代理，也不擅自更改系统网络设置。

- 对用户已选文件读取 SHA-256。复用键是账号/profile/region、目标 projectId、文件 SHA-256 与导入类别；文件名不算内容身份。
  相同文件路径内容已变就按新素材处理；先保留仍被引用的旧素材，不覆盖已批准锚点。
- 用记录中的 nodeId/resourceId 定位，批量 `node show` 读取所需来源节点，核对所选资源成功、类型正确、仍可访问。
  已核实合法的节点批量读取失败时，可缩小批次只读重查；整体读取失败不代表节点不存在，不据此重复创建。实测一次读取 26 个节点返回 `service.2`，拆为每批 10 个后成功；这是本次恢复经验，不是接口固定上限。
  节点被换图时不能复用旧哈希映射。旧记录无哈希时不能仅凭同名认定一致；核对可验证来源或实际内容后再建立映射。
  用户确认已在网页补传指定文件后，用确切标题定位新节点，回读成功状态、上传源文件名和媒体尺寸后复用该节点；保留旧上传的未知状态，不把新节点成功当作旧 resourceId 已恢复。
- 仅上传缺失素材。当前契约支持 `resource upload --file ... --project-id ... --resource-id ... --import-kind ...`。
  上传前为该次素材分配并记录稳定 resourceId，上传后立即回记结果。
  每份素材明确上传失败且可重试时，首次上传后最多再试两次，合计最多三次。每次先核查原资源或原槽位，确认失败后再试。CLI 复用原 resourceId，网页优先重试原失败槽位。
  素材就绪即停止重试。两次重试后仍失败时，记录并报告失败原因，暂停依赖该素材的生成。
- CLI 进程同时捕获 stdout、stderr 和退出码。CLI 1.2.0 的上传错误可能以 JSON 写到 stderr、stdout 为空；应解析实际错误信封，保留 code、requiredAction、resourceId 和 requestId，不能把空 stdout 仅当作 JSON 解析失败。
  遇到 `cli.upload_state_unknown` 时不自动重传，即使沿用原 resourceId；先用原 ID 执行 `resource get --project-id ...` 只读核查。仅在查到成功且类型正确时继续；返回资源未找到仍不能排除远端已创建对象，应停止并报告，不换 ID 或改走网页再次上传。
  用户在获知这一未知状态后明确要求改走已登录网页继续时，按新的授权执行；保留旧 resourceId 与未知状态，单独记录网页上传结果，不把新上传成功写成旧请求已恢复。
- 上传成功只是资源登记，不等于画布已有可见素材节点。每份素材都按资源类型和 schema 用 `node create image` 或 `node create video`
  携带原 `--resource-id`、匹配的 `--import-kind` 及稳定 nodeId/updateId/submitId 挂入画布，不重新上传、不带 `--run`。
  导入 nodeId 格式以当前 schema 为准；不可把裸 UUID 当 Node ID。
  CLI 1.2.0 的本地校验要求显式 Node ID 为 `node_` 加 10 个小写 Crockford Base32 字符；不要截取任意长度的 UUID。使用自动生成 ID 时，保存后立即记录返回值。
- 已有图片节点时直接 `--ref node:<id>`，需要正文定位才使用 `{{node:<id>}}`，保持传入顺序与提示词一致。
  首尾帧按首帧、尾帧顺序；多模态参考按已确认映射，不临时换图，不把多视图说明当唯一主锚点。
  上传完成后批量回读新节点并检查引用；满足项目连续性验收的素材才可进入视频生成。
  CLI 入参 `res:<UUID>` 在回读中表示为 `kind=resource`；比较引用时规范化这种表示差异，保持 ID 和列表顺序逐项相等，不为字符串写法不同重存草稿。
  CLI 1.2.0 的资源引用回读可仅包含 `kind/id/type/writebackSupported`，不内嵌 `resource.status`。引用校验按数量、顺序、类型和 ID 比较；
  就绪状态使用本轮已取得的 `resource get` 结果。可选元信息缺失不等于素材未就绪，不因此误报参考不一致或重新上传。
  网页初次解析 CLI 保存的资源引用时，可能短暂显示“参考素材信息不可用”、加载中的临时编号和不完整价格。
  先让页面完成解析，再只读核对一次真实文件名、顺序、就绪状态及价格；本次解析完成后这些占位状态自行消失。
  不修改提示词或引用来消除加载占位；解析后仍不一致时按用户要求停止。
- CLI 明确不支持所需动作，或符合本节已验证的本机上传故障选路条件时，读取 computer-use 技能走网页；无法确定已经发出的上传是否成功时先查资源/节点，不立刻换途径再传。

- 本机只读对照确认：系统代理为 `127.0.0.1:10808`，默认 CLI 的代理环境变量为空、账号查询直连公网，而 Chrome/ChatGPT 有到该代理的连接。仅在一个 CLI 子进程设置 `HTTP_PROXY`/`HTTPS_PROXY` 为核实的系统代理后，账号查询成功且连接改走本地代理。这证明网络路线不同，尚未证明上传故障由它引起或已修复。以后确有新素材上传任务且用户允许 CLI 验证时，可仅对该子进程使用当时核实的代理做一次正常上传；不永久改环境变量、不关闭证书校验、不额外上传测试文件，未知结果仍按原规则处理。

### 网页建稿与上传（2026-11-05 实测）

- 本次 CLI 1.2.0 的视频草稿保存拒绝已有视频引用中的 `uri`（`service.2`，`Generation reference type uri is not supported when saving a node`）；不可把它当作可保存的节点引用。遵守任务停止条件，用户明确授权后才采用其他方式。
- 新图片走网页上传时，先核验源文件 SHA-256；已登录画布左栏“上传”先注册 `filechooser` 再点击，`setFiles` 指定本地绝对路径，不操作 Windows 文件选择框。回读新图片节点编号、上传源文件名、类型、尺寸和成功状态，视频草稿以 `--ref node:<id>` 按顺序引用，再回读核对。上传状态不明先查画布和原节点，不重复上传。

- 已登录画布的左栏“视频”可新建空节点；双击该节点的 Rename 按钮后填写 Node title，再按 Enter 保存。
  从目标节点 DOM 的 `data-id` 回读编号并立即记入当前任务，续接时只操作这个节点。时长弹窗可直接填写数字输入框，失焦后核对按钮显示值。
- 画布已有的参考选“添加参考 → 从画布选择”。禁止用“添加参考 → 上传参考内容”直传。
- 本次九图批量上传后，成功素材按完成顺序排入列表，三份失败项留在末尾；传入文件数组有序不能证明最终引用有序。
  对编号严格的任务可逐份等待就绪；批量上传则按最终列表核对，网页提供 Shift + 左/右箭头调序。失败项不计为成功引用，未就绪时显示的价格也不是完整草稿报价。
- 本次 `fill` 与纯文本粘贴均丢掉提示词空行；非空行数、去换行字数和 `@` 数量相等仍不足以证明全文一致。
  DOM `innerText` 又会在段落间增加空行，不能直接当作保存正文；CLI 可读时用 `node show` 的 `data.nodes[].node.generation.prompt` 核验。
  本次已确认保存正文少了原文空行，未通过逐字要求，不能宣称原样保存或提交生成；不要为了匹配网页去修改源文件。
- 回读网页上传引用时可能出现 `uri`、`vid`，不能当作 Resource UUID。记录公开节点编号、源文件哈希与可见上传状态；不持久化这些底层存储标识，也不猜测另一种 ID 来续跑。
- CLI 部分素材上传成功、其他素材状态未知时，先查询原资源；用户已明确授权网页补传后，可用已成功的资源先创建本任务唯一的视频草稿，
  通过 CLI 保存完整原文和参数，缺的图片再从画布左栏“上传”补成独立图片节点后引用。不重复上传已成功的资源；保留原未知上传记录。
  本次补传后，`node show` 可读取完整草稿，`node quote/confirm/run` 可直接操作原节点，不必把网页引用改写成另一种 ID。
- 网页补传可能仅将提示词的 CRLF 换行规范化为 LF。本次所有换行和空行均保留，规范化后的全文与回执 `文本sha256` 完全一致。
  验收时分别核对源文件字节哈希、规范化后的全文和文本哈希；若任务明确要求换行编码也逐字节一致，仍按任务要求处理。
  只允许说明已验证的换行编码差异，不能用去掉全部换行、删空行或仅比较行数字数的方式放行内容变化。

## 4. 先准备完，再集中报价与批准

- 每个交付视频一个稳定业务键、一个节点。创建/编辑草稿时一次填齐提示词、模型、时长、比例、质量和有序引用。
  generation 编辑是完整替换：先回读当前 generation，再构造完整的新值并显式指定 mode，不能只传改动字段丢失其他参数。
  不为简单任务额外创建主体、剧本、关键帧、音频或时间轴；不借“快线”重新编写已批准提示词。
- 没有明确积分上限时，先只保存草稿，再对本次待运行节点批量 `node quote`。
  不用无上限 `create/edit --run` 试探价格：服务端免确认时可能直接生成；`--dry-run` 也不能获取真实报价。
- 所有项目均可报价后，将视频名称/数量、关键参数、逐项价格、总价与建议积分上限放在同一条简短请求里。
  只在服务端要求批准、用户要求先审或超出既有授权时暂停；明确批准范围内不再问“是否继续上传/是否提交”。
  部分报价不能冒充整批总价；无法报价或占用未知不当作零，先查明，必要时交回用户。
- 已获本批次明确金额上限时，复用授权。单节点可按 schema 使用 `create/edit video --run --credit-ceiling <已批准值>`。
  多节点用一次 `node confirm` 批准整批上限，再用一次 `node run` 提交相同批次。
  批次总上限不能给每个节点各用一次；参数或数量改变须仍在已授权范围内，涨价超过上限必须重新询问。
- 批准 token 只在内存传给对应调用，不打印、不落盘。不用 `--yes`、伪造确认或修改宿主权限来减少批准步骤。
  只有“加快流程”不等于永久消费授权；不要承诺以后任何情况都只需确认一次。

## 5. 提交后原地恢复

- 副作用前保存 projectId、稳定节点/资源/更新/提交 ID、实际喂料文本及哈希；响应后立即补记公开任务编号与状态。
  多节点 `node run` 的 nodeId 与 submitId 按顺序一一对应；将已批准上限及用户授权范围记入同一任务记录。
- 组合命令退出码 10 且要求确认时，节点已保存、尚未运行；保留 partialData 的 nodeId 和 submitId，获批后续跑原任务。
  不重建节点、不换 submitId；不把等待批准描述为生成失败。
- 网络超时、响应丢失、本地写回失败不证明远端失败。先用 `operation status/wait <submitId>` 只读查询，必要时显式 projectId。
  已受理/运行中/成功项目不再提交；仅按恢复协议处理明确未受理项。无法排除重复扣费时停止重试并说明具体不确定项。
  退出码 20 继续只读恢复；absent 可能是记录过期，unknown 代表无法判断，均不能单凭该状态重提。
  已 claim 的任务不因批准 token 过期重新申请积分；先核对原任务，不把 nodeId 当 operation reference。
- 原操作和资源均明确失败、用户又明确授权重试时，先回读原节点核对提示词、参考、参数及当前报价；原稿未变就复用节点和素材。
  将旧 submitId、resourceId、失败原因与积分事实保留在同一任务的尝试记录里，为新一轮生成分配新的 submitId，按本次授权上限确认后只提交一次。
  不重放旧 submitId，不重建草稿或重复上传；任务书原有的失败后停止限制，仍须由用户当轮明确重试指令覆盖。
- 等待只查询本次任务，使用有界 wait 或逐步退避；避免高频全画布查询和长时间阻塞用户反馈。
  重连先恢复待完成任务，不重跑整条流水线；单项失败不抹掉其他已受理项目。
  网页同时有多个生成任务时，将进度条和视频 DOM 的读取限定到已核验的目标节点容器，不用页面全局匹配推断本次状态。
  CLI 已成功而网页仍显示旧进度时，确认没有本地未保存编辑后可刷新一次，再选中同一节点；刷新和播放不触发重新生成。

## 单视频参考生成 720P 正片：CLI 1.2.0 实测路径

以下路径已实测完成上传、保存、提交、生成和本地下载。用户明确禁止修改生成记录或运行 Git 时，遵从当轮限制，公开身份与回执保留在当前对话，不额外写记录文件。

1. 用 `node ls --project-id <projectId> --name <完整标题> --type video` 定位目标（CLI 1.4.2 起；1.3.0 及以前叫 `node find`，新版不认）；完整标题无结果时再查一次短名。本次两次均无结果，才用 `node create video` 建同名目标。浏览器已有目标画布时直接复用该标签页。
2. 核对本地视频 SHA-256，先照第 3 节查记录和画布，有就引用；没有才以稳定 UUID 执行 `resource upload --file <视频路径> --type video --project-id <projectId> --resource-id <resourceId> --import-kind local_upload`。用 `resource get <resourceId> --project-id <projectId>` 确认 `type=video`、`status=success` 及真实时长。上传后用 `node create video` 挂成独立视频节点，照 AGENTS.md 起名，再以 `--ref node:<id>` 引用。
3. PowerShell 用 `[System.IO.File]::ReadAllText(<提示词路径>)` 读取全文，并把该字符串作为单个 `--prompt` 参数传入；保留换行和字面的 `@视频1`。本次正片参数为 `--mode m2v --model seedance_2.5 --ratio 16:9 --resolution 720p --duration 15 --count 1`，先保存，不带 `--run`。`seedance_2.5_draft` 是样片模型，不能用于该 720P 正片路径。
4. `node show` 回读目标：将 `generation.prompt` 与文件全文做 Ordinal 相等比较，并核对 UTF-8 SHA-256、非空行数、去换行字数和 `@` 数量；检查 `generation.references` 仅一项、指向那个视频节点，模型、分辨率、比例、时长和数量均正确。核对失败就不提交。
5. `node quote` 读取真实报价；在用户已有授权内，用 `node confirm --credit-ceiling <已获准上限>` 取得 token，随即执行一次 `node run --node-id <目标节点> --submit-id <稳定UUID> --credit-token <token>`。token 只在进程内传递，不输出、不落盘；不要把本次价格固化为以后任务的授权。
6. 用同一 submitId 执行 `operation wait <submitId> --project-id <projectId> --timeout 50s --interval 20s`。`cli.operation_wait_timeout` 只说明本次等待窗口结束，继续只读等待，不再次运行。直到 operation 与输出资源都成功，再用 `resource get` 核对 `generationKind=normal`、`resolution=720p` 等实际参数；积分以提交前后 `auth account` 的余额事实核对。
7. **先照第 6 节用命令行下载。** 命令行失败才走浏览器：用画布搜索定位准确标题，选中该节点；从该节点的 DOM 内唯一 `<video>` 读取 `currentSrc || src`，同时核对尺寸和时长。若节点已就绪但只有封面、没有 `<video>`，先点击该节点的播放按钮，再读取媒体源。URL 只放在当前浏览器会话内存，不输出或写入文件。在同一浏览器工具的 JavaScript 会话中，已实测可用以下方式直接写入用户指定文件，无需 Windows 文件选择框或中转目录：

   ```javascript
   const fs = await import('node:fs/promises');
   const crypto = await import('node:crypto');
   // src 来自已选目标节点的 video DOM；output 是已核对的用户目标路径。
   const response = await fetch(src);
   if (!response.ok) throw new Error('视频下载失败：' + response.status);
   const bytes = Buffer.from(await response.arrayBuffer());
   if (!bytes.length) throw new Error('视频为空');
   const file = await fs.open(output, 'wx'); // 同名文件存在即停止，禁止覆盖。
   try { await file.writeFile(bytes); await file.sync(); }
   finally { await file.close(); }
   const actual = await fs.readFile(output);
   if (!actual.equals(bytes)) throw new Error('视频回读不一致');
   const sha256 = crypto.createHash('sha256').update(actual).digest('hex');
   ```

   直接下载出现 `ECONNRESET` 或 SSL 握手超时，但资源已成功时，可改用目标节点的网页“下载”入口；
   不改签名 URL、不猜其他 CDN 域名、不关闭证书校验，也不重新提交生成。先注册
   `tab.playwright.waitForEvent('download', { timeoutMs: 45000 })`，再点击下载，使用事件返回的 `path()` 定位实际文件。
   网页吐司“下载成功”不能代替文件回读。本次该入口下载成功，未经过 Windows 文件选择框。
   点击前核对目标节点的 `data-id` 和 Selected 状态；搜索面板已关闭时先重新打开，再用准确标题定位，不沿用失效的搜索结果。
   定位并选中目标后，若搜索侧栏遮挡播放按钮，先收起侧栏再播放；本次侧栏展开时点击未加载视频，收起后同一播放按钮正常加载。
   浏览器若先生成默认下载目录中的托管文件，只处理下载事件返回的这一份，并立即归位；不得另建中转目录或按文件名通配清理。
   跨盘归位不能用 `os.rename`；目标以 `xb` 独占创建，复制后回读逐字节核对，再清理本轮托管源文件。同名目标存在立即停止。

   浏览器当前文档若暴露 `locator.downloadMedia`，也可直接对已核验目标节点内唯一的 `<video>` 调用
   `downloadMedia({ timeoutMs: 45000 })`，使用其返回的本地路径归位；本次样片下载成功，无需读取或传递签名 URL。
   CLI 提交已受理、后续只读查询连续报 `cli.transport_failed` 时，本次通过同一已登录画布中目标节点的
   `1 ready, 0 processing, 0 failed`、实际播放及本地完整解码确认成功；保留 CLI 查询失败事实，不重提、不补写未取得的 operation 终态。

8. 本次下载后还核验了 MP4 容器、1280×720 视频轨、约 15 秒时长及音轨，并在目标节点播放检查画面。交付时分别报告提交时间和确认完成时间；服务端未给实际完成时间时，不把首次观察成功的时间写成精确完成时间。只保留成片和必要输入，不生成额外截图、逐命令记录或验收文件。

用户要求完整解码时，可用现有 FFmpeg 执行 `-hide_banner -nostdin -xerror -err_detect explode -i <原片> -map 0:v:0 -map 0:a? -fps_mode passthrough -f null -`，
核对退出码和最终解码帧数，不只检查容器头或首帧。封面元数据警告与音视频解码错误分别记录；平台标称时长、帧率和下载文件实测值不一致时，
分别说明来源，以原片实测值交付，不为凑整秒转码或剪辑。抽帧检查可在内存中完成，不新增审片图片或报告文件。

CLI 1.2.0 的 `seedance_2.5_draft` 未暴露独立声音参数，本次网页也无单独开关；不要杜撰 flag 或声称已切换开关。用户要求声音时保留其声音提示，交付前实际验证音轨可解码且非静音；本次样片通过了 AAC 双声道与音量检测，不能据此保证后续每次输出都有声音。
